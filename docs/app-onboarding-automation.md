# Automatic app onboarding

Implemented September 30, 2026 for the versions pinned in each app's `docker-compose.yml`. Changes are in the repository; the running installation has not been upgraded. The target is **Install → Open → use the app**. The first Open establishes a real application session using the user's existing Authentik session. No user cookies are exported to the worker.

SSO and application setup are separate tasks. Authentik handles authentication; per-app adapters create the first administrator, establish ownership, and configure useful defaults. This implementation uses supported configuration, APIs, and management commands rather than browser clicks.

Native Mu3Lab OIDC providers use Authentik's implicit-consent authorization flow, removing the app-consent prompt while retaining the **authorization-code grant**, authentication/MFA, and application access policies. The OAuth implicit grant is not enabled. Proxy-gated services retain their existing authorization configuration.

## Ownership, retries, and credentials

`ctl/onboarding_state.py` stores each installing owner and generated app credential in encrypted runtime records outside the checkout. Key and record permissions are `0600`; writes are atomic and locked. The generated password is persisted before account creation, so an interrupted installation can reuse it. A second operator's repair or retained-data reinstall preserves the stored owner. An initialized Immich instance never receives a replacement administrator. SurfSense retries authenticate the same generated credential rather than resetting an existing user's password.

Generated logins are kept encrypted until successfully written to the owner's Vaultwarden. Unlike the old expiring job handoff, a delayed first visit does not lose them. The existing vault workflow saves all pending logins in one batch, then deletes the durable password copies. Existing unrelated vault entries are preserved; a skipped entry does not count as a successful credential save. The dashboard reoffers vault saving when new pending logins exist, even if an earlier batch was saved. Deleting app data clears its onboarding record; keeping app data preserves it.

Bitwarden's installed extension provides autofill. It cannot expose its unlocked vault to dashboard JavaScript or universally create application accounts. The server-side batch still requires the master password once per batch; it is used only in memory. URI Host matching includes each app's port, avoiding credential confusion on the shared hostname. See [Bitwarden URI matching](https://bitwarden.com/help/uri-match-detection/) and [autofill](https://bitwarden.com/help/auto-fill-browser/).

## Automatic completion and upgrades

The durable worker checks pending native app identities every minute. Only app-specific callback/account evidence queues finalization; a healthy container or an Open click is insufficient. Finalization applies the sign-in policy through the existing lifecycle job and updates initialization state. The user no longer needs a separate Confirm setup or Repair click after a successful first login.

When the dashboard returns, installations whose previously recorded owner matches the current operator (including those already marked ready) can adopt the new durable owner mapping and stage updated sign-in configuration automatically. Unknown legacy ownership requires the existing **Repair sign-in** action; the dashboard does not silently claim those accounts. Failed finalization reports an actionable app error rather than repeatedly recreating containers.

An upgrade must deploy the updated control plane, worker, dashboard build, and app definitions. Existing apps need their current runtime definitions applied before new launcher URLs are available; the adoption job does this once for eligible installations, recording the applied definition version to avoid repeated restarts. A core-suite run applies LobeChat's updated edge launcher and onboarding defaults. Unknown legacy ownership can use Repair sign-in to apply the new definition. Applying these changes recreates the affected app/ingress containers and briefly interrupts access.

## Validation and limits

Backend and dashboard suites cover lifecycle behavior, ownership checks, retries, encrypted storage, and vault handling. Additional checks validate generated Caddy configurations with the installed Caddy version, preserve the served launch script, and exercise Paperless's CSRF launcher with the installed Django version. Upstream/model imports were checked against the running pinned applications without altering their accounts.

A complete signed-in browser walkthrough and fresh-container deployment matrix are still required before claiming every first Open has passed end to end. This tool session has no existing authenticated browser session. In particular, verify actual app callbacks, the managed no-consent flow, existing-account collisions, retained-data migrations, and recovery access on the upgraded deployment. Phone permissions, bank OAuth, external AI-provider accounts/keys, and meaningful app content cannot be inferred from Authentik membership.
