# LiveKit (voice assistant)

A voice assistant people talk to in the browser. Everything runs on this server.

```text
browser ──HTTPS──> voice page (Talk, :8476, Authentik)  ──token──┐
browser ──WSS────> LiveKit signalling (:8477, LiveKit token)  <──┘
browser ──WebRTC─> LiveKit media (tailnet address only: 7881/tcp, 7882/udp)
                       │
                  voice agent ──> LiteLLM (agent's own key)
                                    ├─ mu3lab-voice  → Ollama or outside providers (Settings, Voice Assistant)
                                    ├─ mu3lab-stt    → Speaches (Whisper)
                                    └─ mu3lab-tts    → Speaches (Kokoro)
                  voice agent ──> ContextForge (the person's own key) ──> each app's tools
admin ──HTTPS──> LiveKit admin dashboard (:8478, Authentik operators; its login is sent for you)
```

## How a call starts

There is nothing to set up by hand: no rooms are created in advance and the agent is not
started per call.

1. Opening **Talk** asks the voice page for a token. The page makes up a new room name, and the
   token asks LiveKit to send the agent named `mu3lab-agent` into that room (explicit dispatch).
2. The browser joins the room. LiveKit creates the room on the first join and hands a job to the
   `agent` container, which registered as `mu3lab-agent` when it started.
3. The agent joins the same room, greets the person and listens. When everyone leaves, LiveKit
   closes the room.

The admin dashboard lists the rooms that are open now and who is in each one, including the agent.

The agent reaches LiveKit's media over Mu3Lab's private container network, not the tailnet
address browsers use, so `livekit.yaml` sets `advertise_internal_ip: true`. Without it the agent
joins the room but its audio never connects ("wait_pc_connection timed out" in its log).

## Apps, as the person talking

The voice page puts the signed-in person in the room token: Caddy passes their verified email
and name from Authentik (`copy_identity_headers`), and `voice-ui/token-route.ts` replaces the
starter's token route, so a token always names a real person and the page refuses anyone else.

The agent then works like chat's assistants:

- A **main assistant** answers general questions (it has the household's app guide) and has one
  `open_<app>` tool per app assistant this person may use.
- Calling one **hands the conversation over** to that app's assistant: the app's own
  instructions and only its tools, reached through ContextForge with the person's own key, so it
  sees what they see in the app. `back_to_main` hands it back.
- A tool the app's review does not mark read-only runs **only right after the person says yes**,
  and each yes allows one change (`ConfirmedToolset`). Without a yes the tool tells the model to
  ask first.

The main assistant also has `search_web` while web search is on and the **SearXNG** app is
installed: private search for current facts, with no account or key.

Mu3Lab writes two files to `voice-tools/` whenever chat's assistants are synced (every install
does) and whenever **Settings, Voice assistant** changes; the agent reads both at the start of
each call, so nothing needs a restart:

- `people.json` (`ctl/voice_tools.py`): each person's assistants, keys and read-only tool names.
  Administrators switch an app off for voice under **Tools**, which also checks that each app's
  tools answer.
- `settings.json` (`ctl/voice_settings.py`): responsiveness, interruptions, the voice, the web
  search address and whether full-duplex mode (Labs) is on.

The folder above it is Mu3Lab's user's alone, and the agent mounts it read-only.

## How long a reply takes

The agent logs one line per reply from LiveKit's own measurements: the wait from the end of
speech to the first sound, and its parts (transcript, end of turn, the model's first words, the
first audio). Tool calls log how long they took.

```bash
docker logs mu3lab-livekit-agent-1 2>&1 | grep -E "Reply after|Tool .* took|Web search took"
```

## Install, start and stop

Install and remove it from the Mu3Lab dashboard (Apps). It needs:

- the voice model in **Settings, Voice Assistant** (the agent uses `mu3lab-voice`). Until you save a
  choice there it matches chat's setting in **Settings, AI**. Start stops with a message when the
  model is not chosen, downloaded or routed (`needs_voice_model` rule);
- the Speaches app.

Start and Stop are on the app's page.

## Where things live

- Keys and passwords: generated by Mu3Lab into the app's private settings
  (`/srv/mu3lab/projects/livekit/.env` and `livekit.yaml`, both readable by Mu3Lab's user only).
- The agent's LiteLLM key is registered by the `gateway_key` rule. It works only for
  `mu3lab-voice`, `mu3lab-stt` and `mu3lab-tts`.

## Changing the model or voice

- **Answer model:** choose outside providers or a local model in **Settings, Voice Assistant**,
  independently of chat. The agent always asks for `mu3lab-voice`, so it follows that choice.
- **Voice:** choose it (and try it) in **Settings, Voice Assistant, Voice**; the next call uses it.
- **Speech models:** the same card sets Speaches up again with other Whisper or Kokoro models,
  which every app using speech then shares.

## Bypassing LiteLLM

If LiteLLM adds noticeable delay, point the agent straight at the services in
`docker-compose.yml`:

```yaml
MU3LAB_LLM_BASE_URL: http://ollama:11434/v1
MU3LAB_LLM_MODEL: qwen3.5:4b-q4_K_M   # the exact Ollama tag
MU3LAB_SPEECH_URL: http://speaches:8000/v1
MU3LAB_SPEECH_API_KEY: not-needed
MU3LAB_STT_MODEL: deepdml/faster-whisper-large-v3-turbo-ct2
MU3LAB_TTS_MODEL: speaches-ai/Kokoro-82M-v1.0-ONNX-int8
```

Bypassing LiteLLM also bypasses its per-route thinking setting: the agent sends no reasoning
level, so a model that thinks by default (Qwen 3.5) thinks before every answer. Keep LiteLLM in
the path for local models.

## Speed

A reply waits for, in turn: the end of speech, speech recognition, the answer model's first
sentence and the voice's first sentence. What keeps each short:

- **End of speech:** 0.2 s of silence (`END_OF_SPEECH_SECONDS`; LiveKit's default is 0.5 s).
  The turn detector still waits up to 3 s when the person sounds unfinished. Preemptive
  generation starts the answer before the turn is confirmed.
- **Models already loaded:** Speaches unloads idle models after five minutes and Ollama after ten.
  At the start of each call the agent uses speech recognition and the voice once, and loads a
  local answer model with the call's own instructions; the greeting waits for that (at most
  60 s). Outside providers are not warmed: there is nothing to load, and a request would spend
  their free allowance.
- **Routes, in order, with thinking off:** LiteLLM holds up to three routes for `mu3lab-voice`
  (`ctl/local_models.py`) and tries the next when one fails or its first words are late:
  1. the local model, if one is chosen (Local only or Local first), with thinking `none`: any
     other level becomes Ollama's `think: true`, about 10 s of thinking for Qwen 3.5 4B;
  2. if outside providers are allowed, FreeLLMAPI's voice list `auto:mu3lab-voice` with
     thinking `none`: only models tested to accept it and call tools, in order
     (`apps/freellmapi/hooks.py`, saved at FreeLLMAPI's install);
  3. any outside model (`auto:smartest`) with `low`, the lowest level every model accepts, for
     when the list is used up (each free Gemini model allows about 20 requests a day) or busy.

  A route with another after it gives up after 8 s (local) or 4 s (the list) without first
  words, and without retrying, so a stuck free model (some wait a full minute) hands over
  while the person is still listening. The agent waits up to 30 s for first words.
- **Local context:** Ollama gives every model 51,200 tokens with an 8-bit conversation cache
  (`apps/ollama/docker-compose.yml`); Qwen 3.5 4B then uses 4.1 GiB on the graphics card.
- **The voice on a graphics card:** Speaches' GPU build uses the full Kokoro model; the small
  int8 one moves between card and processor hundreds of times per sentence (about 3 s against
  0.15 s for one sentence on an RTX 3060).
- **Raw audio:** the voice is fetched as 24 kHz PCM, so nothing is encoded or decoded as MP3.
- **Saying what is happening:** handing over to an app's assistant says "Let me check
  Calendar." at once, and a tool that runs over a second with nothing being said gets "One
  moment.", then "Still working on it."

Measured on the owner's server (RTX 3060), October 2026: speech recognition 0.4 s once
loaded; a local Qwen 3.5 4B starts answering in 0.1 to 0.3 s and streams; outside providers
through FreeLLMAPI send each answer in one piece, in about 1 s from Gemini 3 Flash Preview and
anywhere from 1 to 60 s from the other free Gemini models.

## Local development

The agent runs on a desktop too. Create `voice-agent/.env.local` with `LIVEKIT_URL`,
`LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` and the `MU3LAB_*` values, then:

```bash
cd apps/livekit/voice-agent && uv run src/agent.py console
```
