# Voice assistant (LiveKit)

A voice assistant people talk to in the browser. Everything runs on this server.

```text
browser ──HTTPS──> voice page (Talk, :8476, Authentik)  ──token──┐
browser ──WSS────> LiveKit signalling (:8477, LiveKit token)  <──┘
browser ──WebRTC─> LiveKit media (tailnet address only: 7881/tcp, 7882/udp)
                       │
                  voice agent ──stream──> Speech: WhisperLiveKit /v1/listen (words while you talk)
                       └────────> LiteLLM (agent's own key)
                                    ├─ mu3lab-voice  → Ollama or outside providers (Settings, Voice Assistant)
                                    └─ mu3lab-tts    → Speech: Kokoro-FastAPI
admin ──HTTPS──> LiveKit admin dashboard (:8478, Authentik operators; its login is sent for you)
```

## How a call starts

There is nothing to set up by hand: no rooms are created in advance and the agent is not
started per call.

1. Opening **Talk** asks the voice page for a token. The page makes up a new room name, and the
   token asks LiveKit to send the agent named `mu3lab-agent` into that room (explicit dispatch).
2. The browser joins the room. LiveKit creates the room on the first join and hands a job to the
   `agent` container, which registered as `mu3lab-agent` when it started.
3. The agent joins the same room, greets the person and listens. When everyone leaves, LiveKit
   closes the room.

The admin dashboard lists the rooms that are open now and who is in each one, including the agent.

The agent reaches LiveKit's media over Mu3Lab's private container network, not the tailnet
address browsers use, so `livekit.yaml` sets `advertise_internal_ip: true`. Without it the agent
joins the room but its audio never connects ("wait_pc_connection timed out" in its log).

## Install, start and stop

Install and remove it from the Mu3Lab dashboard (Apps). It needs:

- the voice model in **Settings, Voice Assistant** (the agent uses `mu3lab-voice`). Until you save a
  choice there it matches chat's setting in **Settings, AI**. Start stops with a message when the
  model is not chosen, downloaded or routed (`needs_voice_model` rule);
- the Speech app.

Start and Stop are on the app's page.

## Where things live

- Keys and passwords: generated by Mu3Lab into the app's private settings
  (`/srv/mu3lab/projects/livekit/.env` and `livekit.yaml`, both readable by Mu3Lab's user only).
- The agent's LiteLLM key is registered by the `gateway_key` rule. It works only for
  `mu3lab-voice` and `mu3lab-tts`. Speech recognition does not go through LiteLLM: the agent
  streams to WhisperLiveKit with the Speech app's own key (`MU3LAB_STT_KEY`).

## Changing the model or voice

- **Answer model:** choose outside providers or a local model in **Settings, Voice Assistant**,
  independently of chat. The agent always asks for `mu3lab-voice`, so it follows that choice.
- **Voice:** change the Speech app's default voice. The agent picks it up when the app is re-wired.

## How a turn ends

The agent hears you through WhisperLiveKit's Deepgram-style stream (LiveKit's Deepgram plugin
pointed at `/v1/listen`), so the words are already there when you stop talking. Silero notices
the pause after 0.3 s, the local turn detector decides whether you have finished, and the answer
and its first spoken sentence are prepared while it decides (preemptive generation and TTS).

## Bypassing LiteLLM

If LiteLLM adds noticeable delay to the answer or the voice, point the agent straight at the
services in `docker-compose.yml`:

```yaml
MU3LAB_LLM_BASE_URL: http://ollama:11434/v1
MU3LAB_LLM_MODEL: qwen3.5:4b-q4_K_M   # the exact Ollama tag
MU3LAB_SPEECH_URL: http://speech-tts:8880/v1
MU3LAB_SPEECH_API_KEY: not-needed
MU3LAB_TTS_MODEL: kokoro
```

Thinking stays off either way: the agent always sends `reasoning_effort: "none"`.

## Local development

The agent runs on a desktop too. Create `voice-agent/.env.local` with `LIVEKIT_URL`,
`LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` and the `MU3LAB_*` values, then:

```bash
cd apps/livekit/voice-agent && uv run src/agent.py console
```
